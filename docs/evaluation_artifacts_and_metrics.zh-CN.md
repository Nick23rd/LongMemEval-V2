# LongMemEval-V2 评测产物与指标说明

## 1. 评测在衡量什么

LongMemEval-V2 用来评估记忆系统能否从很长的历史操作轨迹中找到与当前问题有关的经验，并将其整理成紧凑、有效的证据，供下游模型回答问题。

完整链路可以概括为：

```text
历史轨迹 → 记忆系统检索与整理 → 记忆上下文 → 固定阅读器回答 → 自动判分
```

因此，这个评测不只关心最终答案是否正确，还关心检索耗时、上下文长度、截断、超时和成本。其核心目标是衡量系统在准确率、延迟和资源消耗之间的实际权衡。

基准包含 web 和 enterprise 两个领域，覆盖静态知识、动态状态、操作流程、易错点以及应当拒答的问题。

## 2. 一次评测会产生什么

一个完整运行目录通常包含：

```text
run_args.json
memory_config.json
per_question.jsonl
aggregated_metrics.json
query_traces/<query_invocation_id>/attempt_*/summary.json
query_traces/<query_invocation_id>/attempt_*/events.json
query_traces/<query_invocation_id>/attempt_*/memory_module_output.json
```

### 2.1 实验配置

`run_args.json` 和 `memory_config.json` 记录本次实验使用的数据、记忆方法、模型、超时、并发和上下文限制等配置。

它们的主要作用是保证实验可复现，并检查两个方法是否在相同条件下运行。没有这些配置，即使两个结果的准确率不同，也很难判断差异究竟来自记忆方法还是模型、数据及参数。

### 2.2 逐题结果

`per_question.jsonl` 每行对应一道题，通常包含：

- `question_id`、问题类别和题目内容；
- 记忆系统返回的上下文及证据；
- 标准答案、模型原始回答和解析后的回答；
- `score`、`score_bool` 和 `is_unknown`；
- Token 用量、查询耗时和上下文截断信息。

这是做逐题配对分析和失败案例分析的主要产物。通过它可以进一步区分：

- 记忆系统没有找到正确证据；
- 找到了证据，但证据不完整或含有噪声；
- 证据正确，但阅读器仍然回答错误；
- 本应拒答时，系统进行了猜测。

### 2.3 聚合指标

`aggregated_metrics.json` 汇总整个运行的结果，包括：

- 总体与分类准确率；
- 正常题和拒答题的表现；
- 平均、P50、P95 和最大记忆查询延迟；
- 阅读器 Token 用量；
- 记忆上下文长度和截断次数。

它适合快速比较方法、生成图表以及制作排行榜提交。

### 2.4 查询轨迹与原始证据

`query_traces` 保存记忆系统每次调用的执行细节：

- `summary.json`：返回码、超时、耗时、命令、用量和所选片段；
- `events.json`：执行过程中的结构化事件；
- `memory_module_output.json`：记忆模块最终返回的原始内容。

这些文件主要用于调试、审计和解释结果。例如，当一道题答错时，可以据此判断问题是出在检索、证据整理、工具执行还是最终回答阶段。

## 3. 准确率指标

### 3.1 总体准确率

`overall_full_set` 表示全部题目的平均得分。在当前二元计分下，可理解为：

```text
overall_full_set = 正确题数 / 全部题数
```

它是最接近最终用户体验的核心指标，因为它衡量整条链路最终能否给出正确答案。不过，它不能独立说明错误发生在哪个环节。

另外两个相关指标是：

- `overall_non_abstention_only`：只统计具有明确答案的普通题；
- `overall_abstention_only`：只统计正确行为应为“不知道”的拒答题。

### 3.2 分类准确率

分类结果用于定位系统擅长和薄弱的记忆能力：

- `static`：相对稳定的环境知识，如固定页面结构或长期规则；
- `dynamic`：会随时间或状态改变的信息；
- `procedure`：完成任务所需的操作步骤；
- `gotchas`：例外情况、隐藏限制及容易踩坑的规则；
- `*-abs`：对应类别中缺少充分证据、应当拒答的问题。

例如，`static` 很高而 `dynamic` 很低，通常说明系统擅长保留固定知识，但不擅长识别最新状态或处理相互冲突的历史信息。

### 3.3 正确、错误与 Unknown

每个类别通常包含：

- `pct_correct`：正确回答比例；
- `pct_answered_wrong`：给出了具体答案但回答错误的比例；
- `pct_unknown`：回答 `unknown` 的比例。

对普通题来说，`unknown` 仍然计为错误；对拒答题来说，正确识别信息不足才是期望行为。将错误回答和 Unknown 分开，有助于区分“错误记忆或错误推断”与“没有找到足够证据”。

## 4. 延迟与稳定性指标

`memory_query` 记录记忆检索本身的耗时：

- `avg_seconds`：平均查询时间；
- `p50_seconds`：50% 的查询不超过该时间；
- `p95_seconds`：95% 的查询不超过该时间；
- `max_seconds`：最慢查询时间；
- `total_seconds`：所有查询累计耗时。

平均值适合做整体资源估算，P50 更接近典型用户体验，P95 则反映长尾等待。记忆系统的耗时分布往往偏斜，因此不能只看平均值。

`memory_post_query` 表示检索完成后的整理、转换等后处理耗时，应与核心检索耗时分开观察。

智能体式记忆方法还应跟踪：

- 超时率；
- 无效输出率；
- 空记忆率；
- 非零返回码比例。

这些指标直接影响系统的上线可用性。一个方法即使成功时准确率很高，如果经常超时或返回空结果，也很难在实际业务中稳定使用。

## 5. 上下文、Token 与成本

### 5.1 记忆上下文

`memory_context` 通常包括：

- `avg_original_tokens`：记忆系统原始返回内容的平均 Token 数；
- `avg_final_tokens`：截断或整理后实际交给阅读器的平均 Token 数；
- `num_truncated_sequences`：因为超过上下文限制而被截断的题数。

记忆上下文不是越长越好。过短可能遗漏关键证据，过长则会增加延迟、成本和噪声，并可能让重要信息被无关内容淹没。理想系统应以较少 Token 返回直接、充分且不误导的证据。

### 5.2 阅读器与智能体用量

聚合结果通常记录阅读器的：

- `prompt_tokens`；
- `completion_tokens`；
- `total_tokens`。

编码智能体的查询轨迹还可能记录输入、缓存读取、缓存创建、输出、推理 Token、轮次和成本。

不同提供商的 Token 语义和缓存价格不同，因此不应只比较 `total_tokens`。更合理的做法是分别报告输入、缓存、输出和实际费用，并进一步计算单问题成本及每个正确答案的成本。

## 6. LAFS：准确率与延迟的综合指标

排行榜使用 LAFS 衡量方法在不同延迟预算下能够提供的最好准确率。其输入为：

```text
准确率 = overall_full_set × 100
延迟   = memory_query.avg_seconds
```

一个方法可以提交多个 operating point，例如快速、平衡和高质量模式。所有有效点共同形成准确率—延迟前沿：如果一个点比另一个点更慢且准确率不更高，那么它是被支配点，不会改善前沿。

LAFS 可以概括为：在对数延迟范围内，对“给定延迟预算下的最好准确率”进行平均。最终提交分数是新方法相对于固定参考前沿带来的增益：

```text
LAFS gain = LAFS(参考前沿 ∪ 新方法) - LAFS(参考前沿)
```

这意味着：

- 更慢但不更准的方法通常没有增益；
- 在某个延迟区间明显提升准确率的方法会得到正增益；
- 同时提供强力的快速模式和高质量模式，可能比单个极慢的高准确率点更有实际价值。

## 7. 如何公平比较两个方法

比较方法时，应使用相同数据、问题集合、层级、阅读器模型和评测配置，并进行逐题配对。每道题可归入：

```text
两者都正确
仅方法 A 正确
仅方法 B 正确
两者都错误
```

这种分析能够显示提升是否来自同一批题，还是两个方法各有不同优势。准确率差异还应配合 McNemar 检验或配对 bootstrap 置信区间，并报告有效样本量。

仅仅多答对一两题，或者只比较两个独立平均值，通常不足以证明一个方法具有稳定优势。

## 8. 如何解读一组结果

建议按以下顺序阅读：

1. 检查样本量、完成率和实验配置是否一致；
2. 查看 `overall_full_set`，判断最终答案质量；
3. 查看普通题和拒答题表现，判断是否存在幻觉倾向；
4. 查看分类准确率，定位具体能力差异；
5. 查看 P50、P95、超时率和无效输出率，判断可用性；
6. 查看上下文 Token、截断率和成本，判断效率；
7. 查看 LAFS，判断方法是否真正改善准确率—延迟前沿；
8. 回到逐题结果及查询轨迹，分析代表性成功和失败案例。

需要特别注意：smoke test 通常只有极少量题目，目的只是验证流水线是否能够运行。即使准确率为 100%，也不能据此判断方法的真实能力。

## 9. 指标总结表

| 指标或产物 | 衡量内容 | 实际含义 / 怎么看 | 主要注意事项 |
|---|---|---|---|
| `run_args.json`、`memory_config.json` | 实验配置 | 判断不同运行是否具备可比性和可复现性 | 模型、数据、层级和超时不同会污染比较 |
| `per_question.jsonl` | 逐题证据、答案和得分 | 用于配对比较、错误归因和案例分析 | 聚合结果无法替代逐题检查 |
| `aggregated_metrics.json` | 整体统计 | 快速了解准确率、延迟、Token 和截断 | 必须结合样本量解读 |
| `query_traces/**` | 记忆系统执行过程 | 判断检索、工具调用、证据整理或回答环节哪里出错 | 可能包含大量原始内容，分享前应脱敏 |
| `overall_full_set` | 全部题目准确率 | 最接近用户最终感受到的回答质量，越高越好 | 无法单独定位错误环节 |
| `overall_non_abstention_only` | 普通题准确率 | 衡量有答案时能否正确回答 | 不体现系统是否善于拒答 |
| `overall_abstention_only` | 拒答题准确率 | 衡量没有证据时能否避免编造 | 需要足够的拒答题样本 |
| 分类准确率 | static、dynamic、procedure、gotchas 等能力 | 用来定位方法擅长或薄弱的知识类型 | 小类别样本少时波动会很大 |
| `pct_answered_wrong` | 明确作答但错误的比例 | 反映错误记忆、错误证据或错误推断 | 应与 `pct_unknown` 分开分析 |
| `pct_unknown` | 回答 Unknown 的比例 | 普通题中反映召回不足；拒答题中可能是正确行为 | 单独追求更低或更高都没有意义 |
| `memory_query.avg_seconds` | 平均记忆查询延迟 | 用于资源规划，也是 LAFS 的延迟输入 | 容易被极慢请求拉高 |
| `memory_query.p50_seconds` | 典型查询延迟 | 代表大多数用户的常规等待体验 | 不体现长尾问题 |
| `memory_query.p95_seconds` | 长尾查询延迟 | 反映较差情况下的用户体验和稳定性 | 对线上体验通常比均值更重要 |
| 超时率 | 未在时限内完成的比例 | 衡量系统是否可以稳定交付结果，越低越好 | 超时题如何计分必须保持一致 |
| 无效输出率 | 输出无法解析的比例 | 衡量接口和格式稳定性 | 高准确率不能抵消频繁的格式失败 |
| 空记忆率 | 未返回有效证据的比例 | 反映检索失败或智能体执行失败 | 应区分合理的无证据和异常空输出 |
| `avg_original_tokens` | 原始记忆长度 | 反映记忆模块最初生成了多少内容 | 长不等于信息充分 |
| `avg_final_tokens` | 实际送入阅读器的记忆长度 | 反映回答阶段真实上下文负担 | 应与准确率和成本一起看 |
| `num_truncated_sequences` / 截断率 | 上下文超限情况 | 反映容量压力和关键证据被裁掉的风险 | 截断位置会影响实际损失 |
| 输入、缓存、输出 Token | 推理资源构成 | 用于分析效率、缓存收益和成本来源 | 不同提供商的字段不能简单等同 |
| 单问题成本 | 每处理一道题的平均费用 | 衡量规模化运行成本，越低越好 | 应说明价格版本和缓存折扣 |
| 每个正确答案成本 | 总成本 / 正确题数 | 同时考虑质量与费用，适合业务决策 | 正确题很少时该值会非常不稳定 |
| LAFS | 不同延迟预算下的最佳准确率 | 衡量方法是否推进准确率—延迟前沿，越高越好 | 使用平均延迟；需与固定参考前沿及相同 tier 比较 |
| LAFS gain | 新方法相对参考前沿的增益 | 大于 0 表示至少在部分延迟预算下带来新价值 | 不是单纯的准确率排名 |
| McNemar / 配对 bootstrap | 差异的统计可靠性 | 判断观察到的优势是否可能只是样本波动 | 应同时报告样本量和置信区间 |
